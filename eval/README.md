# 评测方案（方案先行，代码后补）

Agent 是 ReAct 架构：模型自己决定调什么工具、查几轮，直到它认为证据够了才开口。
这种"自己拿主意"的东西不能靠"我觉得挺好"来验收，得有可复算的数字。

设计原则只有一条：**能机械判的绝不交给模型判，模型只判机器判不了的。**

---

## 一、三层评测集

| 文件 | 层 | 条数 | 测什么 | 单次成本 |
|---|---|---|---|---|
| `cases-gold.jsonl` | 金标（自动生成） | 153 | 检索组件：召回与跨年覆盖 | 0 token，每条 2–22 ms |
| `cases-real.jsonl` | 真实问题（人工） | 27 | 端到端：引用忠实、答对、成本；含复合需求与多轮 | 真金白银，跑一次几十秒 |
| `cases-adv.jsonl` | 对抗（人工） | 12 | 拒答、抗诱导、安全、稳定性 | 同上 |

### 金标为什么不用人工标

概念档案、公司轨迹、认错档案、实体跨年出处**自带 `loc`（哪封信第几段）**，那就是标准答案。
`gen_cases.js` 直接把它们抽出来当 gold，改了语料重跑一次即可，编号稳定。

分布：`entity 116 · company 55 · concept 47 · correction 15 · span 11`（一条 case 可同时属于多类）。

### 金标要分两类看，否则指标没有意义

生成器给每条 case 算了 `corpus_hits`（这个词在全库出现过几次），`needs_alias = corpus_hits === 0`：

- **词面可检索（113 条）**：「可口可乐」这种词本身就写在原文里，字面检索就该命中，召回差就是检索的问题。
- **需别名或档案（40 条）**：「股东导向」「科技与互联网」是人工分类的主题标签，原文里没这几个字；
  「伊藤忠商事」原文用的是简称「伊藤忠」。这两类字面检索本来就接不住，得靠别名表与人工档案补，
  不该拿它们给检索打低分。

### 首次实测基线（153 条全跑，零 token 成本，约 3 秒）

| 分桶 | 条数 | hit@6 | 跨年覆盖 |
|---|---|---|---|
| 全部 | 153 | 81.0% | 63.6% |
| **词面可检索** | 113 | **96.5%** | **75.8%** |
| 需别名或档案 | 40 | 37.5% | — |

结论：检索组件本身是健康的（96.5% 命中），**缺口集中在同义与主题层**——
这正好量化了「同义召回靠人工档案 + 别名表覆盖」这个设计决策的必要性，
也指出了下一步该补的地方：40 条接不住的题，对应的别名表项还没有。

## 二、Trace（可观测性）—— 评测的地基（已落地）

一条问答 = 一个 trace，挂一串 span。服务端（`agent.js` 的 `writeTrace`）按天写到
`eval/traces/YYYY-MM-DD.jsonl`，一行一条，全量落不抽样。实际字段：

```jsonc
{
  "ts": 1762…, "date": "2026-11-02", "time": "19:26:03",
  "run_id": "rb1",              // 线上流量是 "live"，评测跑批由请求传入
  "qid": "real-003", "layer": "real", "session": "…", "vid_hash": "a1b2…",
  "question": "…", "model": "deepseek-flash", "web": true, "mode": "archive",
  "key_source": "free",         // free=站长的免费额度 / byo=访客自带 / eval=跑批专用
  "spans": [                    // 模型轮次与工具调用交错，按发生顺序
    { "i":0, "type":"llm",  "round":1, "ms":2676, "ttft":null, "finish":"tool_calls",
      "prompt_tokens":1460, "completion_tokens":338, "wants_tools":["search_letters","letter_outline"] },
    { "i":1, "type":"tool", "round":1, "name":"search_letters", "args":{"query":"…"},
      "ms":11, "out_chars":2100, "n_sources":6, "error":null }
  ],
  "sources": [ {"kind":"letter","l":"1999 巴菲特致股东信","b":37,"y":1999} ],  // 答案里真正挂了标记的
  "all_sources": 12,            // 这一路上翻过的段落总数（比 sources 多，翻过不等于引用）
  "citations": [ {"kind":"letter","l":"1999 巴菲特致股东信","b":37} ],
  "answer": "……", "usage": {"prompt_tokens":4200,"completion_tokens":610},
  "ms": 21400, "ttft": 18200, "rounds": 3, "calls": 4, "truncated": false, "error": null
}
```

**落盘纪律**：不落密钥、不落访客号明文（只存 sha256 前 16 位）、不落 IP；
线上 trace 与评测 trace 用 `run_id` 分开；线上那份留着排查个案与算真实成本，30 天清一次。

两个坑，踩过才有这些字段：

- **`ttft` 对 agent 的语义和普通聊天不一样**：前几轮都在调工具、一个字都不吐，
  所以 `ttft` 常常等于"最后一轮开始作答的时刻"。看"多久开始吐字"要读 `spans[].ttft`。
- **信件 id 是字符串**（`1999 巴菲特致股东信`），不是数字下标。解析 `[[信|段]]` 的正则
  必须写成 `[[([^|\]]+)\|(\d+)]]`，写成 `\d+` 会一个引用都解析不出来。

判分是**第二遍独立跑**的：读 trace 算分，结果写到 `eval/results/score-<run_id>.json`。
（不是追加回 trace 行 —— 分开存更简单可靠，改判分口径也不用动 trace。）
判分逻辑改了不用重跑 agent —— 重跑一次评测要真钱。

## 三、判分口径

### A. 机械判分（不需要模型，全部可复算）

| 指标 | 算法 | 红线 |
|---|---|---|
| 引用存在率 | 答案里每个 `[[l\|b]]` 查 `L[l].blocks[b]` 是否存在 | ≥ 95% |
| 逐字忠实率 | 答案引号内文本 vs 被引用段落，最长公共子串 ≥ 8 字的比例 | ≥ 95% |
| 数字溯源率 | 答案里每个数字串是否出现在被引用段落原文中 | ≥ 95% |
| 网络来源标注率 | 用了 web 引用时，是否出现"网络来源"字样且与信里原话分开 | 100% |
| 拒答准确率 | 该拒答时拒了 / 不该拒时没拒（对抗层） | ≥ 85% |
| Recall@6（金标） | 前 6 段命中金标段数 / min(6, 金标数) | 待基线 |
| 跨年覆盖（金标） | 前 6 段覆盖了多少个不同的金标年份 | 待基线 |

### B. 模型判分（LLM-as-judge）

只对机器判不了的：有没有正面回答、有没有编造、来源有没有区分、术语有没有解释。
每条 1–5 分，附扣分理由。**盲评**（不告诉 judge 是哪个版本）、**随机顺序**、**双评算一致率**，
一致率低于 0.6 的题说明 rubric 写得有歧义，改 rubric 而不是改答案。

### C. 人工抽检

机械判分全过但 judge 打低分的，人工复核 20%。

## 四、效率与成本（也是机械的）

平均轮数、工具调用次数、首字延迟（TTFT）、**单问 token 与折合人民币**。
最后一个要单独盯：免费 10 次 × 每日 150 问，成本必须算得清。

---

## 五、看板：只盯这五个数

- **引用忠实率 ≥ 95%**（< 90% 视为不可上线，这是产品命根子）
- **答对率（judge ≥ 4 分）≥ 80%**
- **拒答准确率 ≥ 85%**
- **单问成本**（折合人民币，设预算上限）
- **Recall@6**（检索组件单独的体检指标；它掉下来是检索的问题，不是模型的问题）

## 六、防止评测过拟合

评测集不进提示词；留 30 条 held-out 只在改版定稿时跑一次；调参一律对着非 held-out 部分。

---

## 七、为什么自己建，不用 Langfuse

Langfuse 给的是存储 + UI + 人工打分 + prompt 版本，但上面这些核心指标它一条都不会算 ——
score 得我们自己算完再推给它。而自托管要 Postgres + ClickHouse + Redis，
与这个项目"零第三方依赖、双击 start.bat 就跑"的气质冲突，线上单端口沙箱也跑不起那一套；
用云版则意味着每次问答原文都发到别人机器上。

**换的条件**：需要多模型 A/B、prompt 版本灰度、多人协作看 trace，或 trace 量大到 JSONL 翻不动。
届时把 JSONL 导出去即可 —— trace 字段已按 span 结构命名，导出成本低。

## 九、分身模式的判分（第一版已实现）

考据模式的「逐字忠实率」不适用于推演区——它本来就不是原话。分身答案另判，见 `check_sim.js`：

| 指标 | 算法 | 红线 |
|---|---|---|
| 双区格式 | 答案里 `【他确实说过】` 与 `【按这些依据推演】` 齐全且顺序正确 | 必须 |
| 引用能落地 | 原话区每个 `[[l\|b]]` 都能取到真实段落 | 100% |
| 引文逐字 | 引号内文本与被引用段落的最长公共子串 ≥ 8 字 | 100% |
| 越界率 | 推演区出现 `[[` / 引号原话 /「我说过」句式 | 0 |
| 依据覆盖率 | 推演区挂的 `〔案例id〕` ≥ 2 条 | 100% |

**别用「前 N 字整段包含」验逐字**：句尾多一个句号就会把好引文误判成改写（实测 5 条里误报 1 条）。

**还没做**：反事实一致性（换个方向再问，答案骨架应稳定）、时间泄漏（引用段落年份 > 案例判断年份）。
这两项要等 trace 里带上 `mode / persona / case_ids` 才能机械判。

## 十、三件套：跑批 → 判分 → 报告（已实现）

```bash
# 0. 起服务时用 EVAL_NO_QUOTA=1：跑批不走访客免费额度，也不撞全站每日上限
EVAL_NO_QUOTA=1 node agent.js

# 1. 跑批（真金白银，约 20 分钟 / 38 条）
node eval/run_batch.js --run-id rb1 --concurrency 3
node eval/run_batch.js --run-id rb1 --case adv-010,adv-011       # 只补跑几条
node eval/run_batch.js --run-id rb1 --set real --limit 6         # 先小规模看看

# 2. 判分（本地计算，不花钱；--judge 才花钱）
node eval/score.js --run-id rb1                 # 机械判分 + 金标检索体检
node eval/score.js --run-id rb1 --judge         # 加模型判分
node eval/score.js --run-id rb1 --judge --rejudge all   # judge 口径改过之后全量重判

# 3. 报告
node eval/report.js --run-id rb1                # → eval/results/report-rb1.md
```

三个脚本分开，是为了让「改判分口径」不用「重跑批」——跑一次批要真钱，判分不要。
`score.js` 判分是幂等的：已判出的分数沿用，只补判失败的；但 judge 提示词一改，
新旧分数就不可比，必须 `--rejudge all` 全量重判。

### 踩过的坑（都会让评测白跑一趟）

| 坑 | 现象 | 处理 |
|---|---|---|
| `keySource` 写在 try 里 | 一次问答报错就 `ReferenceError`，**整个服务进程退出** | 提到 try 外；`writeTrace` 自己包 try/catch |
| 引用标记正则写成 `\d+` | 273 个引用一个都解析不出来，忠实率恒为 0 | 信件 id 是字符串，用 `[[([^\|\]]+)\|(\d+)]]` |
| judge 用推理模型 + 小 max_tokens | 光思考就吃掉 2500–5800 token，正文 0 字，24/38 条判不出来 | judge 改用非推理模型；要换回推理模型就把额度抬到 8000+ |
| 跑批读流超时没接住 | 一条题超时把整批带崩 | `askOnce` 整体 try/catch + 重试（`--retry`，默认 2 次） |
| 年份按"正文里有没有这几个字"判 | 大量正确回答被误判成捏造数字（55% → 85%） | 年份先查被引信件本身的年份 |
| judge 通用 rubric 用在边界题上 | 考"如实说做不到"的题因没引原文被打 2 分 | 提示词写明：边界题不因缺原文扣分 |
| 拒答准确率用一把尺子量所有对抗题 | 把"要区分来源""要挡住套提示词"也算成必须拒答，压出 36% 的假低分 | 只统计 expect 明确要求拒答的题 |

### 首次端到端基线（rb1，38 条：real 24 + adv 12 + 稳定性重复 2）

| 指标 | 实测 | 红线 | 判定 |
|---|---|---|---|
| 引用存在率 | 100%（273 个引用） | ≥ 95% | 过 |
| 网络来源标注率 | 100%（7 次联网引用） | 100% | 过 |
| judge ≥ 4 分占比 | 89.5% | ≥ 80% | 过 |
| 拒答准确率 | 75%（3/4，只算明确要求拒答的题） | ≥ 85% | 未达 |
| 逐字忠实率 | 45.7%（141 处引号：71 逐字 / 39 引号内改写 / 31 疑似编造） | ≥ 95% | 未达 |
| 数字溯源率 | 74.8%（205 个数字） | ≥ 95% | 未达 |

效率：平均 17.3 s、4.09 轮、9.4 次工具、8,769 token/问，折合约 ¥0.024 一问。

**逐字忠实率这个数怎么读**：它低不等于在编造。141 处引号里 71 处逐字对得上、
39 处是"话是那个意思但打了引号"（轻病：读者会误当成原话）、31 处对不上——
而"对不上"里混着三类盲区：拒答语境、联网引用（本地没正文可核）、长期记忆与模型自述
（本来就不在语料里）。所以它是**指向问题所在的指标，不是终审判决**，低了要抽看。

### 记忆题为什么要单独跑
